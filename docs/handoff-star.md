# Handing vibe-runbook to the STAR agent

**For:** the agent working on STAR with Este.
**Status of the tool:** built, 264 tests, **not published**. Run it from its checkout.
**Written:** 2026-08-13, after a real run against STAR.

## What this is

`vibe-runbook` does two things. It **writes** an operations runbook by inspecting an app, and it
**checks** whether a runbook is still true against a running system. The second is the reason the
first exists: a generated runbook's pins name the command that answers them, so they cannot go stale,
and a later check tells you what has drifted.

It is deliberately not a documentation generator that fills pages. Where it cannot derive something
it writes a question and says so.

## Run it

```bash
cd C:/Users/estev/Projects/Vibe-Runbook/plugins/vibe-runbook
node engine/cli.mjs author --project C:/Users/estev/Projects/STAR --out <somewhere you choose>
```

**It never overwrites.** If a runbook already exists at the target it backs it up and writes a
proposal beside it. Nothing was written into the STAR repo during the run below.

Omit `--env` and it makes **no network calls at all** — the health section becomes a question
instead. That is the safe default and the right one for a first pass.

## The rule that matters most

**Never fill in an `**Unwritten:**` stub by inference.** The stub exists precisely because nothing
could derive the answer. A plausible invention is worse than a visible gap — the whole point of this
tool is that it does not produce confident fiction, and an agent guessing on its behalf destroys
that.

Answer them from what you actually know about STAR, or leave them. Every later check reports the
document as incomplete until they are answered, which is the intended pressure.

## Known limitation on STAR specifically, stated plainly

**The `source` gatherer only reads `package.json`. STAR is Python.** So `pyproject.toml` is never
opened and the run and test commands — `uvicorn`, `pytest` — are missing from the output even though
they are trivially derivable. Same for anything in `azure-pipelines.yml`-style CI config.

That is the single largest gap on this app, it is a known defect rather than a design limit, and it
is queued as the first item of the next plan. If you want the runbook to carry how to run and test
STAR, write those two lines by hand — do not wait for the tool.

## After you fill it in

```bash
node engine/cli.mjs scan --runbook <the runbook> --project C:/Users/estev/Projects/STAR
node engine/cli.mjs walk --env <name> --project C:/Users/estev/Projects/STAR
```

`walk` **hard-stops** if the credential for the named environment is missing. That is correct
behavior, not a failure — a green run against the wrong target reads as evidence, so it refuses
rather than falling back to something local. It never spends and never mutates.

Verdicts you will see: `PASS`, `FAIL`, `BLOCKED` (could not check — not the same as the doc being
wrong), `SPENDS` (checking it would cost money, so it did not), `HUMAN` (real but only a person can
judge it), `QUESTION` (recognized but unclassifiable).

**A past-tense coverage record is never failed.** "The chain walk over all 17 stored rooms" drifts
because rooms were built and deleted, not because the doc lied. The tool reports those and does not
flag them, which is what keeps its FAIL list worth reading.

## How this relates to the smoke list

`docs/smoke-2026-08-12.md` is a *verification* runbook — pre-demo, per-step right/wrong, cost
annotated. This generates an *operations* runbook — how to run, deploy, roll back, what breaks. They
are different genres and both are useful. The smoke list is also what this tool was built against:
walking it is what found the 422-instead-of-401 defect and the two stale header pins.

## What to report back

If the generated runbook is useless on STAR, say so and say why — that is a more valuable result than
a polite one. The measured derivation rate on two other real apps was about 1%, and the honest
question is whether the questions it asks are worth the run even when the answers it derives are thin.
